# 趣灵 aha-flash — 产品与路线

> 文档定位：记录长期产品真相、交互质量标准和当前路线。临时输入文档放入 `docs/input-docs/`，完成整合后归档。

## 1. 产品定位

趣灵（aha-flash）是一款 AI 原生交互式知识学习引擎。

一句话：把复杂概念和长篇信息编译成可互动的小组件，让用户通过操作、反馈和顿悟来理解知识。

核心差异：

- 不以长篇解释为主要输出，而以 Generative UI 为主要输出。
- 不只解释“是什么”，还让用户在交互中看到机制如何运转。
- 不使用通用教学模板，而是结合用户状态、兴趣和知识盲区生成个性化隐喻。

## 2. 目标用户

| 用户画像 | 核心痛点 | 典型场景 |
|---|---|---|
| 非专业背景学习者 | 专业术语门槛高，长文难读 | 快速理解金融、科技、商业概念 |
| 职场学习者 | 时间碎片化，需要快速建立认知 | 通勤或工作间隙学习一个复杂概念 |
| 知识爱好者 | 信息源很多，但消化成本高 | 把长文、视频、播客变成可玩的理解路径 |
| 年轻用户 | 传统学习形式枯燥 | 像玩小游戏一样理解抽象知识 |

## 3. 核心体验

用户输入：

```text
期权是什么？用我能听懂的方式讲。
```

系统结合用户状态：

- 背景：非金融专业
- 爱好：抽卡游戏
- 知识盲区：金融基础
- 隐喻偏好：游戏机制

系统输出一个可交互组件，例如“期权抽卡模拟器”：

- 用户先支付一小笔“期权费”。
- 再观察未来结果。
- 如果高价值结果出现，可以按锁定价行动。
- 如果没有出现，最大损失只等于期权费。

用户通过一次点击和反馈理解：

```text
期权 = 未来选择权 + 有限损失 + 上涨收益暴露
```

## 4. 已实现能力

- 首页工作台：输入、对话、状态面板、互动组件渲染。
- Generative UI Schema：V2 `pattern/template/payload`，兼容 V1。
- 10 类交互 Pattern：概率、参数探索、记忆卡片、时间线、对比、测验、系统搭建、分支故事、分类、模拟推演。
- Stateful Memory：背景、爱好、隐喻偏好、知识盲区、已学概念、关键洞察。
- 知识沙盒：`/sandbox` 中按主题回看已学概念。
- 学习深度：快懂、场景、映射三档。
- 质量体系：固定 case、Schema 评分、Prompt 对比。

## 5. 核心功能边界

### Stateful Memory

系统维护轻量用户状态，记录背景、爱好、知识盲区、隐喻偏好、已学概念、最近学习主题、关键洞察和理解深度。

原则：

- V1 使用匿名用户 ID + localStorage。
- 不保存全量对话原文，只保存压缩状态和必要短期窗口。
- 已学概念以轻量资产记录，只保留概念名、Pattern、Template、理解深度和主题域。
- 当前学习线程记录概念、追问深度和最后一次用户输入；换题时归档为短线程摘要。
- 用户可以在知识沙盒中按主题回看已学概念地图。
- 学习深度分为 `rapid`、`scenario`、`mapping`。
- 生产持久化最终应迁移到数据库或 KV。

### Intent And State Reflection

每轮对话先判断用户意图：

- `knowledge`：解释、对比、测验、学习概念。
- `preference`：表达背景、爱好、偏好、希望换一种讲法。
- `casual`：与学习无关的闲聊。

每轮结束后提炼用户新偏好、当前理解深度和可写入状态的摘要。

### Personalized Metaphor

系统根据用户状态选择隐喻域：

| 用户兴趣 | 隐喻域 | 适配概念 |
|---|---|---|
| 抽卡游戏 | 概率、锁价、资源投入 | 期权、保险、投资组合 |
| 赛车 | 速度、策略、进站 | 算法复杂度、竞争策略 |
| 音乐 | 节奏、和弦、结构 | 数学、编程、系统关系 |
| 烹饪 | 配方、火候、比例 | 化学、系统架构 |

隐喻生成原则：

- 优先使用用户熟悉领域中的真实机制、道具、动作或规则。
- 不强行把所有领域抽象成通用“等级”。
- 当道具名可能误导概念结构时，用“领域名词 + 原理标签”双层表达。
- 交互动作必须映射概念机制，而不是只换皮。

### Generative UI

LLM 输出结构化 UI Schema，前端按 `pattern + template + payload` 渲染互动组件。

Schema 可附带：

- `next_concepts`：推荐 1-2 个相邻概念。
- `depth`：控制快懂、场景、映射三档解释密度。

当前交互模式：

| Pattern | 用途 | 当前模板 |
|---|---|---|
| `probability` | 概率、期权、保险 | `card_flip_reveal`, `spin_wheel` |
| `parameter_explore` | 参数影响、因果变量 | `single_slider`, `dual_slider` |
| `concept_memory` | 术语记忆、概念映射 | `term_cards`, `grid_match` |
| `process_timeline` | 历史、流程、演化 | `horizontal_timeline`, `vertical_scroll` |
| `comparison` | 对比、辨析、权衡 | `split_panel`, `overlay_fade` |
| `knowledge_check` | 测验、理解检查 | `single_question`, `combo_chain` |
| `system_builder` | 系统、模块、架构 | `module_sandbox`, `flow_connect` |
| `narrative_branch` | 案例、决策、逻辑谬误 | `branch_story` |
| `classification_sort` | 分类、归因、边界判断 | `category_buckets` |
| `simulation_play` | 复利、供需、网络效应 | `parameter_simulation` |

## 6. 输入来源策略

当前主路径：

- 用户直接输入文本。
- 学习完成后的知识链推荐。
- `/sandbox` 知识沙盒回看已学概念。

产品判断：

- 趣灵核心是把已有概念翻译成交互隐喻，不以联网查新信息为核心能力。
- 不把“复制 YouTube URL 再粘贴回来”设计成主路径。
- URL 抓取只作为低频高级入口或技术兜底；Round 2 已标记网络搜索与 URL 自动路由为待删除项。

远期自然入口：

- 截图/图片上传：OCR 或视觉理解后转成可交互知识组件。
- 音频/视频文件上传：转写后提取知识点。
- 系统分享入口：从浏览器、视频应用、播客应用直接分享给趣灵。
- 剪贴板快速导入：粘贴文本、截图或混合内容。

## 7. 页面信息架构

趣灵不是聊天应用外加一个组件预览区。主界面只保留用户完成理解所需的信息。

目标布局：

- 顶栏：48px，高度固定；左侧 Logo + 趣灵，右侧知识沙盒与设置入口。
- 主区域：交互组件垂直居中；空态只提示“输入一个概念开始探索”。
- 底部输入栏：固定在底部，承载概念输入、下一步概念推荐和深度引导。

应删除的首页可见信息：

- 当前状态调试面板：`userId`、背景、输出类型、交互计数等字段不在首页展示。
- 状态摘要面板：最近主题、关键洞察、会话摘要不在首页展示。
- 对话历史面板：互动结果在组件里，不用消息流竞争注意力。
- 工作台标题和重复设置按钮。
- body 网格线背景。

## 8. 互动组件质量标准

组件目标不是“暗色卡片里放文字”，而是让用户看见概念机制。

视觉标准：

- 每个 Pattern 有独立主色，而不是全局绿色一把梭。
- 全组件暗色层级必须拉开，`#07120f` / `#091611` / `#0c1915` 这类肉眼难分的近似色不再作为相邻层级。
- 表面色、容器色、抬高色至少有 15% 亮度差。
- 标题、副标题、正文、辅助文字、关键数值有固定层级。
- 卡片、按钮、标签、进度条使用统一圆角规则。
- 间距遵循 8/16/20/24px 的清晰节奏。

Pattern 主色：

| Pattern | 主色 | 语义 |
|---|---|---|
| `probability` | `#F7C948` | 稀有/价值 |
| `parameter_explore` | `#36D399` | 可调节 |
| `concept_memory` | `#78A6FF` | 记忆/认知 |
| `process_timeline` | `#B392F0` | 时间流动 |
| `comparison` | `#F4A261` | 对比/差异 |
| `knowledge_check` | `#FF6B6B` | 正确/错误 |
| `system_builder` | `#35E69B` | 连接/构建 |
| `narrative_branch` | `#E879BA` | 选择/分支 |
| `classification_sort` | `#4DD9C1` | 分类/归位 |
| `simulation_play` | `#FACC15` | 模拟/推演 |

字体层级：

| 层级 | 规格 | 用途 |
|---|---|---|
| 标题 | `text-2xl font-semibold` | 概念名 |
| 副标题 | `text-base font-medium` | 步骤/阶段名 |
| 正文 | `text-sm leading-relaxed` | 解释文本 |
| 辅助 | `text-xs text-[var(--muted)]` | 标签/提示 |
| 数值 | `text-3xl font-bold` | 关键数字 |

禁用：

- `text-lg` 作为标题。
- `text-xl` 作为正文。
- `gap-3` / `gap-7` 等非 4 的倍数间距。
- `rounded-[8px]` 硬编码。
- 组件文件中直接硬编码 Pattern 色值。

间距与圆角：

| 类型 | 规格 |
|---|---|
| 组件内边距 | `p-5` |
| 卡片间距 | `gap-4` |
| 区块间距 | `gap-6` |
| 行内间距 | `gap-2` |
| 卡片/面板 | `rounded-xl` |
| 按钮 | `rounded-lg` |
| 标签/badge | `rounded-md` |
| 进度条 | `rounded-full` |

交互标准：

- 每个组件覆盖 entering、idle、interacting、result、empty、error 六态。
- 主 CTA 有明确可点击反馈。
- 关键数字、结果揭示、成功/失败状态必须有语义化动效。
- 所有可点击元素最小高度 44px。
- 深度切换不在顶部提前让用户选三档；默认先给“看一眼”，完成交互后在组件下方/输入框上方用内联引导进入下一档。

状态与微交互参数：

| 状态/交互 | 视觉表现 |
|---|---|
| entering | 250ms fade-in + translateY(16px) 到 0 |
| idle | 主 CTA 使用 `ui-breathe`，opacity 0.9 到 1，周期 2s |
| interacting | 按钮 disabled + spinner，操作区高亮边框 |
| result | 反馈区 `ui-result`，关键数字 `animate-value-pop` |
| empty | `EmptyState` 从中心渐入 |
| error | 组件级 ErrorBoundary |
| 按钮按下 | scale(0.96) 到 1，150ms ease-out |
| 卡片选中 | border-color 变化 + scale(1.02)，200ms |
| 数值变化 | scale(1.3) 到 1，300ms spring |
| 结果揭示 | opacity 0 到 1 + translateY(8px) 到 0，400ms ease-out |
| 成功 | `animate-success-flash`，400ms |
| 失败 | `animate-error-shake`，300ms |

可及性：

- 所有按钮必须 `cursor-pointer`。
- 图标按钮必须有可理解的 `title` 或 `aria-label`。
- 滑块必须有 `aria-label`。
- 深色背景上的文字对比度目标不低于 4.5:1。

内容标准：

- `title` 必须短而具体。
- `description` / `quote` 要包含具体场景。
- `insight` 至少包含一个因果链。
- `explanation` 要说明错在哪里和正确是什么。
- 数组字段至少 3 项。
- Prompt 的正例反例必须同时约束结构和内容，不只约束 JSON 类型。

### 深度渐进

三档深度使用渐进式引导：

| 档位 | 用户动作词 | 系统行为 |
|---|---|---|
| `rapid` | 看一眼 | 默认，一个交互先看懂概念是什么 |
| `scenario` | 试一下 | 完成后引导代入真实场景做决策 |
| `mapping` | 拆开看 | 场景完成后引导拆开原理映射 |

规则：

- 不在输入前展示三按钮。
- 只提示下一档，不回头提示上一档。
- 引导文案是内联文字，不是并排按钮组。
- 点击引导后走完整 API 重新生成该深度 Schema。

## 9. 隐喻生成语言

全局规则：通用语打底，领域语翻译。

- 先用平实中文说清概念动作。
- 再用用户熟悉领域的真实机制、道具、动作或规则做对应。
- 选定术语体系后全文统一，禁止混用。
- 每个抽象概念必须有具体对应物，禁止“像玩游戏一样”这种泛类比。
- LLM 不拿固定术语表硬套，而按“拆动作 -> 找机制 -> 验映射 -> 统一术语 -> 给对应物”推理。
- 推理结果写入 payload 的 `metaphor_trace` 字段，前端不渲染，仅用于调试、评估和回归。

隐喻推理流程：

1. 拆解概念的核心动作：这个概念在做什么，用 1-2 个动词概括。
2. 在用户领域找行为最接近的机制。
3. 逐一验证映射是否成立，选成立度最高的。
4. 选定一个术语体系后全文统一，禁止混用。
5. 每个抽象概念必须有具体对应物，禁止泛类比。

## 11. 非功能需求

| 需求 | 指标 |
|---|---|
| 首屏加载 | 目标 < 2s |
| 组件生成 | 目标 < 10s |
| Schema 稳定性 | 非法输出可修复或 fallback |
| 质量回归 | 固定 case 覆盖全部 Pattern、深度和意图 |
| 移动端 | 核心交互可用 |
| 可访问性 | 交互控件有语义标签 |
| 状态体积 | 轻量、可压缩、可迁移 |

## 12. V1 不做

- 用户注册/登录
- 多设备同步
- 付费订阅
- 社交系统
- 完整内容审核后台
- 离线模式
- 生产级长期记忆数据库

## 13. 成功指标

| 指标 | 目标 |
|---|---|
| 从输入到看到组件 | < 10s |
| 交互完成率 | > 70% |
| 隐喻相关性用户自评 | > 85% |
| 状态偏好匹配满意度 | > 80% |
| 传统长文本解释占比 | 尽量低，优先 UI |
